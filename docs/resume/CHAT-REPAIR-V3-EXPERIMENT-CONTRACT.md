# Alpha chat repair v3 — rollout-conditioned repetition-unlikelihood contract

**Contract state:** locally implemented and unexecuted on NVIDIA

**Training authorization:** not implied by this document

**Public model:** unchanged until every admission gate passes

**Sealed-final suite:** remains closed

## 1. Purpose

Alpha's public checkpoint can begin many ordinary replies, but it is not yet a dependable conversational model.
Repair v2 made every development response nonempty while increasing repeated trajectories and failing to produce
a reliable relevance gain. More ordinary clean SFT is therefore not the next experiment.

Repair v3 tests one new causal intervention:

> Does adding train-only, model-trajectory unlikelihood at mechanically identified repetition onsets reduce
> Alpha's free-generation loops without sacrificing response initiation, relevance, natural repetition, or clean
> stopping?

The intervention is called **rollout-conditioned repetition unlikelihood** (RCR-UL). It is a structural repair,
not a claim that repetition is Alpha's only weakness. Even a positive result does not authorize public promotion
unless ordinary conversational quality also passes the declared review.

## 2. Why this intervention is next

The 2026-08-01 mechanism analysis found:

- v2 created more new loops than it fixed at every checkpoint;
- loop onset was usually around generated token 18–24;
- only 3 of 68,964 supervised targets crossed the same repetition threshold;
- 110 of 214 dominant generated loop phrases were absent from all supervised targets;
- a calibrated embedding diagnostic found no reliable semantic-contingency gain;
- both continuation and clean-base CE controls failed.

This is the pattern expected when a model behaves acceptably under gold prefixes but falls into regions induced
by its own generations. RCR-UL exposes the model to those prefixes and lowers the probability of the exact token
that completes an already-repeated local cycle.

The design follows the intervention class established by:

- [Welleck et al.](https://arxiv.org/abs/1908.04319), who introduce unlikelihood training for repetitive text;
- [Li et al.](https://aclanthology.org/2020.acl-main.428/), who extend it to dialogue repetition and undesirable
  continuations;
- [He and Glass](https://aclanthology.org/2020.acl-main.185/), who train against failures generated by the model;
- [Guan and Huang](https://aclanthology.org/2023.findings-acl.431/), who use a model's earlier repetition bias as
  a self-contrastive negative signal.

Alpha's exact masking, engine implementation, matched control, and behavioral selector are project-specific.

## 3. Single changed variable

The causal variable is the scalar weight on the RCR-UL loss:

| Arm | Positive CE | Train-only failed rollout branch | RCR-UL weight |
|---|---|---|---:|
| **C0 — matched control** | yes | executed with the same tensors and masks | 0.0 |
| **U1 — RCR-UL** | yes | executed with the same tensors and masks | 0.5 |

Everything else must match:

- initialization checkpoint and exact bytes;
- optimizer reset policy;
- learning-rate schedule;
- seed and batch order;
- positive and negative cohort IDs;
- positive token weights;
- number of forward and backward calls;
- number of optimizer steps;
- checkpoint schedule;
- evaluator source, prompts, decoding, and limits;
- GPU type within a paired run;
- source commit and dirty-state contract.

The control must execute the negative branch with a zero upstream gradient rather than skipping it. This matches
the candidate's data movement, graph construction, forward pass, backward pass, and optimizer-step schedule. If a
zero-gradient branch changes parameters, the implementation fails its preflight test.

No second unlikelihood weight, alternative n-gram size, response-length penalty, semantic-negative objective,
decoding penalty, corpus mixture, or architecture change is admitted into v3. Those would be later experiments.

## 4. Objective

For a train-assigned conversation prefix `x` and its accepted assistant response `y+`, retain the ordinary
assistant-only positive loss:

```text
L_CE = - sum_t M+_t log p_theta(y+_t | x, y+_<t) / max(sum_t M+_t, 1)
```

`M+` retains the selected checkpoint's proven positive weighting policy:

- user, padding, and delimiter targets: weight 0 where already defined by assistant-only masking;
- the first four assistant content targets: weight 8;
- the terminal assistant EOS target: weight 2;
- other assistant targets: weight 1;
- EOS is never counted as an answer-start token.

From the same prefix, the frozen selected checkpoint greedily produces `y-`. Define `R_t=1` only when all of the
following hold:

1. the position belongs to generated assistant content, not a prompt or role marker;
2. `y-_t` completes a token 4-gram that already appeared earlier in the same generated assistant response;
3. the full generated response crosses the existing declared degenerate-loop threshold;
4. the position is at or after the first repeated 4-gram onset;
5. the token is not EOS.

The negative loss is:

```text
L_UL = - sum_t R_t log(max(1 - p_theta(y-_t | x, y-_<t), epsilon))
       / max(sum_t R_t, 1)

L_total = L_CE + lambda * L_UL
```

with `lambda=0.0` for C0, `lambda=0.5` for U1, and a numerically declared `epsilon` no larger than `1e-6`.

The implementation must compute `-log(1-p)` directly. Negating cross-entropy or maximizing ordinary CE is not an
equivalent objective and is not allowed: it is unbounded, penalizes probabilities incorrectly, and could corrupt
unrelated vocabulary.

## 5. What the loss deliberately does not penalize

RCR-UL does not make repeated words or phrases globally illegal. Natural dialogue needs repetition for:

- names and terms under discussion;
- correction and emphasis;
- parallel construction;
- quotation;
- lists, mathematics, code, and poetic form;
- short acknowledgements across turns.

The loss acts only on repeated token 4-gram completion positions in preserved failed rollouts. There is no global
no-repeat list, vocabulary blacklist, minimum-length rule, post-hoc deletion, forced EOS, or decoding-time n-gram
block.

## 6. Data boundary and leakage prevention

### 6.1 Positive data

Positive responses come only from the immutable v2 train split:

    /mnt/donto-data/donto-resources/research/
      alpha-chat-repair-v2-r2-20260731/train.txt

The rendered train SHA-256 remains:

    5307b6ec210a172f853f7d5ba353727e1a6f065a337154954b049d989f403f63

No AlphaCorpus candidate, development response, v2 generated output, sealed prompt, or user-written evaluation
judgment may enter the training cohort.

### 6.2 Rollout cohort

Before renting a GPU, construct a deterministic candidate index from train-assigned conversations:

1. parse and validate role boundaries with the native tokenizer;
2. select the final assistant turn as the positive target and all preceding turns as its prompt;
3. exclude any row whose prompt plus the 128-token generation reserve exceeds the selected checkpoint's native
   512-token context;
4. exclude rows whose positive assistant target is empty or structurally invalid;
5. group dynamically by manifest source metadata;
6. rank within each source by `SHA256(contract_seed || stable_conversation_id)`;
7. allocate a balanced total of 4,096 conversations without a hand-maintained source-name switch;
8. preserve selected and excluded IDs with reasons and hashes.

Source balancing operates from the manifest's discovered groups and counts. It must not contain an `if` ladder
over source names.

### 6.3 Frozen negative generation

Generate exactly one greedy rollout per selected prefix from the immutable public native checkpoint:

    399f776b49acc0c8834ff8a7f2390454e2c5f2d833a264e3f83ff546e973cfec

The reference generator is Alpha's native cached decoder. A batched stock-Transformers execution of Alpha's
already parity-proven export may accelerate the complete ledger only after a frozen 24-row cross-source smoke
passes all of the following against native output:

- exact prompt, generated-content, stop-token, and complete token trajectories;
- exact selected and runner-up token identities at every generation step;
- chosen/runner-up logits and log-sum-exp within `1e-3`;
- chosen-token probability within `1e-5`;
- one native checkpoint SHA, one export weight SHA, deterministic fp32, TF32 disabled;
- a hash-bound parity report that is required by the mask compiler and whose accelerated rows match the prefix
  of the complete rollout ledger.

If any parity condition fails, the accelerated ledger is inadmissible and generation falls back to the native
path. Provider-generated text, API generation, quantized inference, stochastic decoding, and an unverified
export are never substitutes.

Generation contract:

- native Alpha inference path or the admitted parity-proven fp32 Transformers acceleration above;
- correct `<|assistant|>` boundary with no trailing standalone space;
- greedy decoding;
- maximum 128 completion tokens;
- no temperature sampling;
- no repetition penalty;
- no minimum-length suppression;
- stop only on learned EOS, role-boundary protection, or token cap;
- preserve prompt IDs, token IDs, text, logits needed for audit, stop reason, and output hash.

The checkpoint is frozen for the entire rollout build. Do not regenerate negatives from intermediate v3
checkpoints; that would change the intervention into online training.

### 6.4 Negative eligibility

A rollout becomes a negative branch only if the existing evaluator marks it `degenerateLoop=true` and at least
one `R_t` position exists. All non-looping rollouts remain preserved in the ledger but receive no unlikelihood
gradient.

Do not use a model judge, embedding threshold, phrase blacklist, or manual “this sounds bad” label to create v3
negative masks. The first experiment isolates mechanically observable repeated trajectories.

### 6.5 Cohort freeze

Before training, produce:

- positive cohort JSONL;
- raw rollout JSONL;
- RCR-UL mask JSONL or packed binary;
- exclusions JSONL;
- source/count audit;
- prompt and output hash manifest;
- tokenizer identity;
- contamination comparison against every development and final ID;
- summary of eligible negatives, penalty positions, onset distribution, and token distribution.

The cohort becomes immutable after its manifest hash is written into the run contract.

## 7. Fresh development selector

The v2 development outputs have now been inspected extensively. They remain useful for regression, but they are
not the primary v3 selector.

Before generating any v3 candidate:

2. require valid roles, a nonempty final user turn, a nonempty source assistant response, and generation eligibility

3. exclude every ID or normalized prompt in v2 development, the fixed v2 qualitative panel, the old frozen final,
   the v2 sealed final, and the v3 rollout cohort;
4. use deterministic hash ranking within dynamically discovered source groups;
5. freeze all 96 prompts, 24 panel IDs, source responses, categories available in manifest metadata, and hashes;
6. record the process before either C0 or U1 trains;
7. do not replace difficult prompts after seeing Alpha's output.

The 24-case qualitative panel is selected by hash before candidate generation. It must contain a controlled mix
of prompt lengths and source groups using computed quantiles, not handpicked promising cases.

The exact eligible-69 v2 comparison remains a secondary paired regression suite. The v2 sealed-final and previous
untouched final suites remain closed.

## 8. Engine implementation

### 8.1 New primitive

Add a masked unlikelihood primitive with a CPU reference and Helios implementation:

```text
crossEntropyUnlikelihoodMasked(logits, negativeTargets, mask, epsilon)
```

Required forward behavior:

- stable log-softmax or equivalent probability computation;
- `-log(max(1-p_target, epsilon))` at masked rows;
- weighted mean over positive mask mass;
- exactly zero loss when mask mass is zero;
- no host readback on the model-sized GPU path.

Required backward behavior at masked row `i`:

```text
d L_UL / d z_{i,k}
  = p_bad/(1-p_bad) * (1{k=bad} - p_k) * normalized_mask_i
```

subject to the declared epsilon clamp and upstream gradient. Unmasked rows must have exactly zero gradient.

### 8.2 Trainer branch

Add an explicit experiment mode; do not overload ordinary CE semantics silently. Each optimizer step consumes a
matched positive batch and its paired failed-rollout branch. Positive and negative gradients accumulate before
the optimizer update.

Metrics per step and checkpoint must include:

- `positive_ce_loss`;
- `negative_ul_loss` before lambda;
- `ul_weight`;
- positive supervised-token mass;
- negative penalty-position mass;
- number of examples with at least one penalty;
- mean and maximum bad-token probability;
- first/last penalty position;
- total combined loss;
- gradient norm before and after clipping;
- NaN/Inf counts;
- step timing split for positive and negative branches;
- peak allocator use and free-range overflow counter.

### 8.3 Expected source files

The implementation is expected to touch only the necessary engine and experiment files, likely:

- `packages/autograd/src/ops.ts`;
- the backend interface that owns cross-entropy primitives;
- `packages/helios/src/backend.ts` and its new Vulkan kernel;
- `packages/train/src/data.ts` for immutable paired batches;
- `packages/train/src/trainer.ts` for the explicit two-branch step;
- focused CPU, GPU, masking, finite-difference, and zero-weight tests;
- native and accelerated rollout generators, a fail-closed parity verifier, a mask compiler, and a v3 launcher.

Exact files may differ after code inspection. The implementation must not modify the v2 launcher or evidence.

## 9. Required local and NVIDIA proofs

No paid training begins until all local reference tests pass.

### 9.1 CPU correctness

- hand-computed two-class and multi-class forward values;
- finite-difference gradient agreement;
- masked rows exactly zero in forward contribution and gradient;
- zero-mask batch returns finite zero;
- upstream gradient scales the result correctly;
- epsilon clamp remains finite near `p_bad=1`;
- lambda zero produces byte-identical parameter updates to a positive-only reference step;
- serialization and resume preserve paired-data cursor and RNG state.

### 9.2 GPU parity

Extend the fail-closed NVIDIA gate. It must execute, not skip:

- CPU/GPU forward parity;
- CPU/GPU backward parity;
- weighted mask parity;
- zero-mask behavior;
- zero-upstream-gradient behavior;
- mixed-precision behavior if enabled;
- one complete paired optimizer step against the CPU reference;
- deterministic replay of that step;
- no CPU fallback on model-sized tensors.

The existing expected NVIDIA assertions must still pass. A test count increase is expected; changing the gate to
ignore new tests is not acceptable.

## 10. Bounded run configuration

Both arms start from the same immutable selected native checkpoint and reset optimizer state because this is a new
objective phase. Both use the same reset.

| Setting | Contract |
|---|---|
| Arms | C0 then U1, sequentially |
| Optimizer | AdamW, newly initialized in both arms |
| Steps | 400 per arm maximum |
| Preservation checkpoints | every 50 steps |
| Declared selector checkpoints | 50, 100, 200, 400 only |
| Learning rate | `5e-6` cosine-decayed to `1e-6` |
| Warmup | 50 steps |
| Positive batch | 16 conversations unless preflight memory proves a smaller matched value necessary |
| Negative batch | exact paired rollouts for the same positive IDs |
| Gradient clipping | existing proven `1.0` policy |
| Context | native 512-token checkpoint limit; prompt at most 384 tokens plus a 128-token reserve; no migration or silent truncation |
| Positive start/EOS weights | 8x first four content tokens; 2x EOS |
| RCR-UL lambda | C0 `0.0`; U1 `0.5` |
| Seed | one declared shared seed |
| Checkpoint selection | fresh development generation, never validation loss alone |

If preflight shows the paired branches exceed memory, reduce the matched batch in both arms and increase gradient
accumulation to preserve the same effective positive and negative example count. Do not change only one arm.

No flagship continuation follows automatically. The 400-step boundary is terminal for this contract.

## 11. Hardware and spend policy

Use one GPU. The proven Vulkan path, correct driver extensions, and available memory matter more than the product
name. A more expensive GPU is justified only if a short, finite preflight demonstrates that Alpha's actual paired
step benefits in throughput per dollar or makes the required batch feasible.

Operational rules:

- never leave an unbootstrapped billing pod idle;
- bootstrap, run the fail-closed gate, and verify real progress before training;
- `nice` local CPU-heavy work and monitor both disks and host memory;
- report real checkpoint/row deltas rather than trusting a “started” message;
- preserve and verify artifacts before terminating compute;
- pause before project-owned new artifacts exceed 15 GiB;
- terminate the pod immediately after both arms and verified recovery, or earlier on rejection.

## 12. Evaluation schedule

At steps 50, 100, 200, and 400 for both arms:

1. run the fresh 96-prompt development selector with identical greedy decoding;
2. recompute raw structural metrics from generated token IDs;
3. run the exact eligible-69 v2 regression comparison;
4. render the frozen 24-case qualitative panel without source-response leakage into Alpha's prompt;
5. compute the supporting BGE contingency diagnostic on one common nonempty population;
6. preserve every output, prompt hash, checkpoint hash, evaluator commit, and summary;
7. make no checkpoint-selection decision from validation loss alone.

Do not evaluate undeclared intermediate checkpoints because a chart looks promising.

## 13. Primary endpoint and admission gates

### 13.1 Primary causal endpoint

On the fresh 96-prompt selector, U1 must beat C0 on paired loop transitions:

- at least 30% fewer total loop flags than C0;
- at least twice as many C0 loops fixed as C0-clean prompts newly looped;
- no more than two new loops on prompts that are clean in both the initial checkpoint and C0;
- lower mean 4-gram repetition than both C0 and the initial checkpoint.

If the selector contains too few C0 loops for the 30% criterion to represent at least three cases, the experiment
is underpowered and may be labelled inconclusive; it may not be called a pass from one changed case.

### 13.2 Structural preservation

U1 must also:

- produce nonempty responses on at least 95/96 prompts and not lose any response that is nonempty in both the
  initial checkpoint and C0;
- have structural passes no lower than C0;
- have EOS termination no lower than C0 by more than one prompt;
- have zero role-marker leaks;
- introduce zero NaN, Inf, allocator-overflow, or truncated-artifact events.

### 13.3 Semantic and conversational preservation

The automatic repetition pass is insufficient. On the frozen 24-case panel, a blinded comparison must assess:

- direct response to the user's actual move;
- coherence under the model's own continuation;
- completeness without lecture-like padding;
- natural stopping;
- absence of parroting and template-without-payload failures;
- preservation of legitimate repetition;
- whether the reviewer would continue the conversation.

U1 must have more wins than losses against C0 and against the initial checkpoint. Any apparent automatic gain
that consists mainly of shorter, evasive, empty, or semantically unrelated answers is a rejection.

The BGE prompt/output and output/reference paired means must not show a reliably negative shift. They are a
regression alarm, not the final quality authority.

### 13.4 Public-promotion gate

Passing the causal endpoint only makes U1 a **stable continuation candidate**. Public replacement additionally
requires:

- aggregate conversational improvement, not merely lower repetition;
- a fresh human-reviewed multi-turn panel;
- no regression on the v2 eligible-69 suite;
- successful execution of the still-sealed v2 final exactly once;
- regression reporting on the older frozen final, explicitly labelled as previously inspected and therefore not
  an untouched selector;
- native/Hugging Face logit parity;
- complete recovery upload;
- an honest model card with remaining failures.

If U1 fixes loops but does not improve conversation, preserve it as a research checkpoint and proceed only under
a separately authorized semantic-contingency experiment. Do not replace the public model.

## 14. Early-stop and rejection rules

Stop an arm and preserve its evidence if any of the following occurs:

- NVIDIA gate failure or skipped expected assertion;
- model-sized CPU fallback;
- non-finite loss or gradient;
- allocator free-range overflow;
- checkpoint cannot be reloaded with exact optimizer/RNG/data cursor;
- at a declared checkpoint, nonempty responses fall below 90/96;
- total loop flags exceed both the initial checkpoint and matched control by at least 20%;
- role leakage appears;
- the cohort or evaluation contamination check fails;
- raw artifacts cannot be copied and hash-verified.

At step 200, U1 may continue to 400 only if it is not already mechanically dominated by C0 on loops,
structural passes, nonempty responses, and EOS together. A loss-only improvement never overrides this stop.

## 15. Interpretation matrix

| Result | Interpretation | Next action |
|---|---|---|
| U1 beats C0 on loops and preserves conversation | The model-specific prefix intervention works | retain candidate; run admission sequence |
| U1 lowers loops but becomes terse, empty, or irrelevant | Objective breaks attractors by avoidance | reject public promotion; inspect mask/weight before any new run |
| U1 and C0 are indistinguishable | Weight/cohort is ineffective or mechanism incomplete | label inconclusive or reject; do not extend steps blindly |
| Correct and zero-weight controls diverge before lambda | Implementation or determinism failure | invalidate run and repair locally |
| C0 improves over initial while U1 does not | Conservative CE continuation, not UL, caused gain | reject causal hypothesis; preserve C0 only if all gates pass |
| U1 helps v3 selector but regresses v2 eligible-69 | narrow selector overfit or source-specific effect | reject public promotion |
| Larger-capability control later learns but current Alpha does not | foundation adequacy limit | make a separate one-GPU foundation decision |
